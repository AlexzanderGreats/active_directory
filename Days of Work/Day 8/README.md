# 07 Controlled And Automated Teardown

1. The Plan

    - my existing generators establish a fairly clear ownership boundary:
        - The MDA schema defines the accounts and groups, while the OU hierarchy defines where those objects live.
    - The generator is already idempotent
        - its second run recognizes existing OUs, groups, users, and memberships instead of duplicating them.
    - The teardown should therefore follow the same philosophy in reverse:
        - If the generator can establish a known state, the teardown should be able to return the lab to a known state without touching unrelated domain objects.

    - AD dependencies mean the order matters, so I'll be using:

    ```Graphic
    1. Validate schema
        ↓
    2. Resolve MDA objects
            ↓
    3. Display destruction plan
            ↓
    4. Remove generated users
            ↓
    5. Remove generated group memberships
            ↓
    6. Remove generated groups
            ↓
    7. Remove empty departmental OUs
            ↓
    8. Remove empty structural OUs
            ↓
    9. Optionally remove MDA root OU
            ↓
    10. Report results
    ```

    - Or more specifically

    ```Graphic
    Users
    ↓
    Group memberships
    ↓
    Groups
    ↓
    Department OUs
    ↓
    Users / Privileged Accounts / Groups / Workstations / Servers
    ↓
    MDA
    ```

    - The root OU should be the last possible thing removed, and I am making that an explicit switch.

2. The First remove_mda.ps1

    - At some point, I will want to add a stritcter ownership mechanism before calling it a 'final version.'
    - Mainly because I am at the point in this project where I should introduce an explicit concept of `Generated by MDA automation`.
    - I already started doing this with my vulnerable schema metadata with something like:

    ```Script
    "generated": true,
    "password_classification": "weak",
    "intentional_vulnerability": "..."
    ```

    - The vulnerable-schema generator therefore already has the beginnings of an ownership/metadata model.
    - I'd eventually extend the generated schema with something like:

    ```Script
    {
        "metadata": {
            "generator": "MDA",
            "generator_version": "1.0",
            "schema_type": "baseline",
            "generated": true,
            "domain": "MDA.com",
            "root_ou": "MDA"
        }
    }
    ```

    - Then the teardown can say:

    ```Graphic
    Is this actually an MDA-generated schema?
        │
        ├── NO → STOP
        │
        └── YES
              ↓
        Continue teardown
    ```

    - That gives me another safety layer beyond merely checking for `MDA_*` or `OU=MDA...`
    - Making the project much more interesting.

    - I also want to split destruction into levels...
    - Level 1: Preview — The Dry run. Nothing would change, but it would output such as:

    ```Powershell
    .\remove_mda.ps1 `
        -JSONFile .\ad_schema.json `
        -WhatIf
    ```

    ```Graphic
    ========================================
    DESTRUCTION PLAN
    ========================================

    Users to remove:  15
    Groups to remove: 15

    [WOULD REMOVE USER] arthur_river
    [WOULD REMOVE USER] adm_arthur_river
    [WOULD REMOVE USER] scott_kang
    ...

    [WOULD REMOVE GROUP] MDA_Surveillance
    [WOULD REMOVE GROUP] MDA_Surveillance_Chiefs
    ...
    ```

    - Level 2: Accounts and groups — removes the generated users and groups but leaves the OU structure.

    ```Powershell
    .\remove_mda.ps1 `
        -JSONFile .\ad_schema.json
    ```

    - That is useful if I am going to be experimenting with the same organizational architecture repeatedly.

    - Level 3: Full MDA environment — can be cleaned up provided the OUs are empty.

    ```Powershell
    .\remove_mda.ps1 `
        -JSONFile .\ad_schema.json `
        -RemoveOUs
    ```

    - Now:

    ```Graphic
    Users
    Privileged Accounts
    Groups
    Workstations
    Servers
    departmental OUs
    ```

    - Level 4: Nuclear option — Laborator reset.

    ```Powershell
    .\remove_mda.ps1 `
        -JSONFile .\ad_schema.json `
        -RemoveOUs `
        -RemoveRootOU
    ```

    ```Graphic
    MDA.com
    │
    ├── MDA OU exists
    │
    └── MDA OU removed
    ```

    - The latter should be an explicit decision because it fundamentally removes the organizational container created.

3. Instead of going through with implomenting the `remove_mda.ps1` file fully, I took on implomenting the ownership concept.

    - With such a necessary identifier for the `remove_mda.ps1`, I decided tow ork on `ad_schema.json` and `gen_ad.ps1` to imploment a feature to update the existing schema.
    - I particularlly want to imploment the metadata to the core users and accounts so when push comes to shove, I can avoid deleting them if I wanted to keep them.

    - I added a `metadata` section on the `ad_schema.json` file already, now I'm moving onto updating `gen_ad.ps1` with the features I want to automate the updates.
    - Now with that functionality added to `gen_ad.ps1`, we can move onto modifying `remove_mda.ps1` by requiring ownership metadata before removing an object.

    - Besides, that, this is a decent excercise. I'm not just generating a fresh environment anymore, I'm changing the managment model of an environment that already exists.

    - Implomented the changes both `gen_ad.ps1`, `ad_schma.json`, and `remove_mada.ps1`.
    - I am not going to copy them over from the Managment controller/ workstation into the Domain Controller, and go from there.
